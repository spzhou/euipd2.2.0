# 第 7 章 产品经理（`PDM`）

## 7.1 定位与菜单

产品经理是研发主线的“发起者与收口者”：从预立项开始，把需求变成特性，推动立项，主持评审，最后发布产品并处理质量与迭代。

| 项 | 说明 |
| --- | --- |
| 角色码 | `PDM`，来自产品经理名单 |
| 菜单 | 14 项：8 项通用 + 绩效/盘点、预立项管理、立项管理、评审管理、产品管理、质量管理 |
| 页签 | 绩效/盘点中可见管理驾驶舱、项目仪表盘、组织工作量；不可见物料盘点 |
| 不包含 | 项目管理、研发管理、物料管理、系统工程、测试管理 |
| 主要交接对象 | 系统工程师（审核与复核）、项目经理（执行）、监管委员（审批）、测试主管（测试） |

产品经理不直接给研发人员派工，派工由项目经理在“研发管理”完成；产品经理也不做特性定义的编写，编写由执行人在工单中完成。

## 7.2 预立项管理

### 7.2.1 适用角色与目的

产品经理、产品总监、项目经理、最终管理人。目的：为一个产品版本建立预立项，作为需求、特性与后续立项的容器。

### 7.2.2 入口

`研发管理 > 预立项管理`（资源号 `5207`，路由 `/customer/character`）。

### 7.2.3 页面构成

| 区域 | 内容 |
| --- | --- |
| 列表 | 预立项名称、所属产品、主开发版本、产品经理、系统工程、状态 |
| 页签 | 需求管理、特性管理（含待签审、待评价）、升级/迭代、修订 |
| 操作 | 新建、编辑、提交、关闭、发起立项 |

### 7.2.4 新建预立项

#### 操作步骤

1. 进入预立项管理，点击【新建预立项】。
2. 填写名称。
3. 选择所属产品；产品不存在时选择“新建”，填写产品名称，产品随之建立。
4. 填写主开发版本。
5. 选择系统工程。
6. 填写预立项介绍。
7. 保存。

#### 字段说明

| 字段 | 必填 | 规则 | 示例 |
| --- | --- | --- | --- |
| 预立项名称 | 是 | 机构内可辨识 | `CUS-预立项一` |
| 所属产品 | 是 | 选择已有产品或新建 | `CUS-智能监控产品` |
| 主开发版本 | 是 | 同一产品下唯一；格式建议四段 | `01.00.0001` |
| 产品经理 | 是 | 默认为创建人 | 钱一品 |
| 系统工程 | 是 | `SM` 成员 | 吴一工 |
| 预立项介绍 | 否 | 文本 | —— |

#### 结果与留痕

保存后状态为 `DRAFT`（草稿），所属产品同步为 `DRAFT`。有需求提交或特性提交后预立项转 `ACTIVE`。同一产品下主开发版本重复时不保存。

#### 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 保存被拒，提示版本重复 | 同产品已有相同主开发版本 | 换版本号；或改用该产品既有预立项 |
| 提交后仍是草稿 | 尚无已提交的需求或特性 | 先推进需求与特性 |
| 想改主开发版本 | 已锁定 | 特性已审批后版本锁定，需走迭代 |

### 7.2.5 预立项修订

预立项在推进过程中如所属产品、系统工程等需要调整，走修订而不是直接编辑已审批内容。修订会留痕并生成新的编辑记录，审批通过后合入主线。

### 7.2.6 关闭预立项

确认该版本不再推进时关闭预立项。关闭后不能再发起立项；如需重启，新建预立项。

### 7.2.7 发起立项

预立项下特性已达 `APPROVED` 后，在预立项中点击【发起立项】，进入 7.5。

## 7.3 需求下发

### 7.3.1 适用角色与目的

产品经理。目的：把已提交的需求转成需求工单，指派给执行人编写特性定义。

### 7.3.2 入口

`预立项管理 > 需求管理`（或 `需求识别` 列表）。

### 7.3.3 前置条件

需求状态为 `SUBMIT`，且属于本产品/预立项。

### 7.3.4 操作步骤

1. 打开需求列表，定位待处理需求。
2. 点击【下发】。
3. 选择执行人（研发工程师等）。
4. 填写计划提交时间与计划工时。
5. 提交。

### 7.3.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 执行人 | 是 | 本机构在职成员；其后按负荷校验 |
| 计划提交时间 | 是 | 日期；受工作日历影响 |
| 计划工时 | 是 | 小时；执行人未来 5 个工作日日均负荷不得超上限 |

### 7.3.6 结果与留痕

工单状态 `HANDLING`，需求转 `HANDLING`，执行人“执行管理”出现待办与角标。执行人提交后需求工单进入审核，回到产品经理或系统工程师。

### 7.3.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 提示工作超负荷 | 执行人未来 5 个工作日日均负荷超上限 | 换人、延长计划时间或减少工时 |
| 需求不在列表中 | 需求未提交或不属于本预立项 | 让提出人确认归属并提交 |
| 下发后执行人没看到 | 未刷新或未登录 | 刷新页面；确认执行人正确 |

## 7.4 特性定义与审批

### 7.4.1 适用角色与目的

产品经理是特性的审批人。特性由执行人在需求工单中编写，经系统工程师给出审核意见后，由产品经理审批并核定功能预算。

### 7.4.2 入口

`预立项管理 > 特性管理 > 待签审`；评价工单在 `待评价`。

### 7.4.3 前置条件

特性状态为 `SUBMIT`，且系统工程师已给出审核意见（工单下一节点已转到产品经理）。

### 7.4.4 审批步骤

1. 打开待签审列表。
2. 逐条打开特性详情，核对名称、六节正文、产品经理、系统工程。
3. 核定功能预算：开发工时、内测工时。
4. 选择【批准】或【驳回】；驳回必须填写意见。
5. 保存。

### 7.4.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 开发工时 | 是 | 数值，进入特性预算 |
| 内测工时 | 是 | 数值 |
| 审批意见 | 驳回必填 | 文本，记入过程与办理记录 |

### 7.4.6 结果与留痕

批准后特性为 `APPROVED`，生成特性版本号（主开发版本加四位编号，如 `01.00.0001-0001`）；相关需求随特性挂接转为 `COMPLETED`。驳回后特性回 `SAVED`，退回执行人修改，审核意见保留。

审批完成后特性版本锁定，主开发版本不再允许修改。

### 7.4.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 待签审为空 | 系统工程师尚未给出意见 | 催办评审节点；核对工单下一节点 |
| 无法改主开发版本 | 已有特性审批通过 | 走迭代生成新版本 |
| 驳回后执行人收不到 | 工单未随驳回回到处理中 | 核对需求工单状态 |

### 7.4.8 特性修订

已批准特性需要改内容时走修订：下发修订工单，执行人修改后提交，系统工程师与产品经理均可审批，通过后版本编号加一，原版本留档。同一特性同时只允许一个修订在进行。

## 7.5 立项申请

### 7.5.1 适用角色与目的

产品经理。目的：把已批准的预立项特性组织成项目，明确团队、里程碑与预算，提交监管委员审批。

### 7.5.2 入口

两条路径：

1. `预立项管理 > 发起立项`（常用）。
2. `立项管理 > 【创建特性开发项目】`（同一机构只能有一个特性开发项目）。

### 7.5.3 前置条件

- 预立项状态为 `ACTIVE`。
- 至少一条特性为 `APPROVED`。
- 已确定监管委员、项目经理、系统工程、测试主管。

### 7.5.4 操作步骤

1. 在预立项中点击【发起立项】。
2. 填写项目名称与项目代码。
3. 选择监管委员、项目经理、系统工程、测试主管与核心成员。
4. 填写激励政策与计划发布时间。
5. 手工添加里程碑（如 M1 立项完成、M2 开发完成）；发布里程碑由发布时间自动生成，不需手工添加。
6. 为每项纳入的特性指定本项目里程碑。
7. 填写预算表（材料费、工时费、其他费用）。
8. 如选用已发布 CBB，在集成特性清单中选用（候选只列已发布 CBB）。
9. 保存为 `SETUP_EDIT`，核对后提交。

### 7.5.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 项目名称 | 是 | —— |
| 项目代码 | 是 | 机构内唯一 |
| 项目分类 | 否 | 取自立项分类 |
| 监管委员 | 是 | `IPMT` 成员，立项审批人 |
| 项目经理 | 是 | `PJM` 成员 |
| 系统工程 | 是 | `SM` 成员，本项目 BOM 复核人 |
| 测试主管 | 是 | 立项批准后取得 `TM` |
| 特性清单 | 是 | 每项特性须指定里程碑 |
| 里程碑 | 是 | 特性引用的里程碑不可删除 |
| 预算表 | 是 | 各科目正数；特性预算之和不得超项目预算合计 |
| 集成特性清单（CBB） | 否 | 只列已发布 CBB，标签为“名称 发布版本” |

### 7.5.6 结果与留痕

保存后项目为 `SETUP_EDIT`；提交后为 `SETUP`，特性同步为 `SETUP`，监管委员收到待办与角标。批准后项目与根子项为 `SETUPED`，预立项转 `CONVERTED`，生成项目基线（含各特性锁定版本与选用 CBB）。

### 7.5.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 项目代码冲突 | 已有同名代码 | 换代码 |
| 里程碑删不掉 | 已被特性引用 | 先改特性的里程碑再删 |
| 提交后驳回 | 里程碑日期或预算不合理 | 按意见调整后重新提交 |
| 已立项项目想再加特性 | 不应新建项目 | 用“追加”把特性追加到已立项项目 |

## 7.6 评审（产品经理作组长）

### 7.6.1 适用角色与目的

产品经理默认担任特性评审、子项目评审与变更评审的组长，并负责审结。目的：汇总委员意见，给出结论并决定是否发布为 CBB。

另有两类评审不由产品经理审结：主项目评审由监管委员任组长（9.15），里程碑评审由主项目经理任组长（9.16）。变更评审的发起入口在特性正文的版本面板（17.6.4）。

### 7.6.2 入口

- 审结：`执行管理 > 任务列表 > 评审主单 > 任务处理`。
- 查看意见：`评审管理 > 评审意见`页签。

### 7.6.3 前置条件

- 评审主单为 `HANDLING`。
- 委员已全部提交意见（可配置为必须全部提交）。
- 若选择“作为特性发布”，特性的物料清单须已提交且覆盖所选 CBB。

### 7.6.4 操作步骤（审结）

1. 打开评审主单，进入审结页。
2. 查看各委员意见。
3. 选择结论：通过 / 有条件通过 / 增补 / 驳回。
4. 通过时选择是否“作为特性发布”。
5. 有条件通过填写条件与计划完成时间。
6. 增补填写增补要求与计划完成时间。
7. 提交审结。

### 7.6.5 四种结论的结果

| 结论 | 特性结果 | 附加动作 |
| --- | --- | --- |
| 通过（发布） | `ARCHIVED`，物料清单锁定，生成特性基线，特性仓库新增 CBB | 派 CBB 定义工单（子项目场景）或直接生成 CBB |
| 通过（不发布） | `ARCHIVED` | 不生成 CBB |
| 有条件通过 | `ARCHIVED` | 派收尾任务，按条件跟进 |
| 增补 | 保持 `DEV_COMPLETE`，增补任务完成后写回 `REVIEW` | 派生增补任务给项目经理，未完成时不能再次审结 |
| 驳回 | 回 `INTEGRATION`，集成工单回 `HANDLING` | 由项目经理修复后重提，再评 |

### 7.6.6 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 审结被拒（委员未提交） | 还有委员未提交 | 催办委员单 |
| 审结被拒（增补任务未完成） | 上一轮增补未闭环 | 等增补任务评价完成 |
| 发布失败（门槛） | 物料清单缺失或六节正文不完整 | 补齐清单与正文后重试 |
| 评审意见页签空白 | 尚未审结 | 属正常，审结后才汇总 |

### 7.6.7 CBB 定义工单

子项目评审选择发布时，会派发 CBB 定义工单给组长。操作：在 `执行管理` 打开该工单，填写集成级 CBB 名称与六节正文，选用子项目范围内的 CBB，提交；同一工单再次进入“任务处理”时是审核视图，审核通过后 CBB 发布。

### 7.6.8 特性评审的发起与前置

特性评审由项目经理在 `研发管理 > 特性评审` 页签发起。发起前须完成该特性相关领料的物料处置并复核（发起页前提条件“费用化物料处理全部完成”）。产品经理在此阶段只作为组长与委员接触评审。

## 7.7 产品管理

### 7.7.1 适用角色与目的

产品经理、产品总监。目的：把完成的项目发布为产品版本，维护基线与停产。

### 7.7.2 入口

`研发管理 > 产品管理`（资源号 `5218`）。

### 7.7.3 页面构成

| 区域 | 内容 |
| --- | --- |
| 产品台账 | 产品列表与状态 |
| 已发布产品 | 已完成项目列表，行内有【发布产品版本】【归档】【特性管理】【质量成本】 |
| 产品版本 | 展开产品查看发布版本，行内有【基线】【停产】 |

### 7.7.4 发布产品版本

#### 前置条件

项目状态为 `COMPLETE`（项目评审通过后）。

#### 操作步骤

1. 进入“已发布产品”，找到目标项目。
2. 点击【发布产品版本】。
3. 选择产品配置（默认现行配置）。
4. 填写发布说明。
5. 上传交付文件。
6. 确认发布。

#### 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 发布版本 | 是 | 按项目主开发版本生成，唯一 |
| 产品配置 | 是 | 下拉，默认现行配置 |
| 发布说明 | 否 | 文本 |
| 交付文件 | 否 | 附件，进入发布基线 |

#### 结果与留痕

发布成功提示；产品由 `DRAFT` 转 `ACTIVE`；新增发布版本并生成发布基线，基线含各特性锁定版本、CBB、锁定的物料清单快照与交付文件。对同一项目重复点击发布不会新增版本。

#### 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 没有“发布产品版本”按钮 | 项目未完成，或本角色无产品管理 | 先完成项目评审；核对角色 |
| 版本号重复 | 同产品已有该发布版本 | 核对项目主开发版本 |
| 发布后看不到基线 | 基线在版本行【基线】 | 展开产品版本再点 |

### 7.7.5 停产

发布版本行【停产】将版本置 `EOL`。全部发布版本 `EOL` 后产品才为 `EOL`。停产不删除历史数据，只表示不再维护。

### 7.7.6 项目归档

`已发布产品 > 项目行【归档】`。归档人限主项目产品经理与监管委员；仅对主项目操作一次即可级联其下子项目；存在未结束子项目时整体拒绝。归档后项目为 `ARCHIVED`，档案树可查。

### 7.7.7 质量成本

在已发布产品行内查看质量成本，显示该项目下各质量单的处理成本，用于质量成本统计。

## 7.8 质量管理

### 7.8.1 适用角色与目的

产品经理。目的：接收质量反馈，下发处理工单，审核分析，给出结案反馈，形成闭环。

### 7.8.2 入口

`研发管理 > 质量管理`（资源号 `5213`）。

### 7.8.3 处理流程

| 步 | 动作 | 状态变化 |
| --- | --- | --- |
| 1 | 质量反馈单提交后进入质量管理列表 | 质量单 `SUBMIT` |
| 2 | 【下发】质量处理工单给执行人 | 工单 `HANDLING` |
| 3 | 执行人填写分析五项并提交 | 质量单 `JOB_SUBMIT` |
| 4 | 产品经理【审核】：驳回或批准并评分、评价 | 驳回回 `SAVE_ANALYSIS`；批准后工单 `COMPLETED` |
| 5 | 【结案反馈】填写反馈描述并提交 | 质量单 `RECHECK` |
| 6 | 提出人复核：通过归档，不通过退回 | 通过 `ARCHIVED`；不通过 `REJECT` 并回到质量列表 |

### 7.8.4 分析五项

问题描述、本质分析、解决方案、输出指标、验证方法。五项齐备才能提交；驳回时须写明缺项。

### 7.8.5 结果与留痕

每步留办理记录。结案后进入质量成本统计。质量工单的领料复核人为产品经理（见 13.7）。

### 7.8.6 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 列表无新单 | 提出人未提交或关联项目不符 | 核对质量单状态与关联项目 |
| 无法结案 | 工单未完成 | 先完成审核与评价 |
| 复核被退回 | 结案反馈不充分 | 补充说明后重新提交 |

## 7.9 迭代与修订

### 7.9.1 适用角色与目的

产品经理。目的：对已发布产品做版本升级，修订既有特性、加入新特性，形成新的预立项与立项。

### 7.9.2 入口

`产品管理 > 已发布产品 > 项目行【特性管理】 > 【版本升级】`（项目迭代对话框）。

### 7.9.3 操作步骤

1. 打开项目迭代对话框。
2. 填写迭代项目名称。
3. 选择升级方式（如功能版本），系统按规则计算新主开发版本。
4. 勾选要迭代的特性。
5. 确定，生成新预立项（所属产品沿用源项目）。
6. 在预立项中下发迭代定义工单，执行人修订定义。
7. 系统工程师给审核意见，产品经理审批。
8. 迭代记录 `APPROVED` 后发起立项。

### 7.9.4 字段与校验

| 项 | 规则 |
| --- | --- |
| 新主开发版本 | 不得与源版本相同，也不得与同产品既有预立项重复 |
| 升级方式 | 决定版本计算规则 |
| 特性清单 | 只能选状态允许迭代的特性；已迭代的不能再选 |
| 所属产品 | 沿用源项目，不可改 |

### 7.9.5 结果与留痕

原特性记录保持 `ARCHIVED` 不变，迭代标记为已迭代；新预立项下生成迭代记录（`UPDATE`），审批后版本前缀为新主开发版本。新项目立项时可选首轮发布的 CBB。

### 7.9.6 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 版本相同被拒 | 手工改成旧版本 | 用系统计算值 |
| 特性不能再迭代 | 已在其他迭代中 | 查该特性迭代标记 |
| 新预立项缺系统工程师 | 一般会沿用源项目 | 手工补选 |

## 7.10 绩效/盘点的产品经理视角

`绩效/盘点 > 项目仪表盘`（`520003`）可查看项目维度的进度、工时与成本。管理驾驶舱与组织工作量对产品经理不可见。

## 7.11 与其他角色的交接

| 交出物 | 交给谁 | 接收方动作 |
| --- | --- | --- |
| 需求工单 | 执行人 | 编写特性定义并提交 |
| 特性（待签审） | 系统工程师先审、产品经理后批 | 出审核意见 → 审批并核定预算 |
| 项目（`SETUP`） | 监管委员 | 批准或驳回 |
| 子项目、特性分配 | 项目经理 | 分解、启动研发、派工 |
| 评审主单 | 委员 | 提交意见 |
| 评审结论 | 项目经理 | 按结论修复、重提或收尾 |
| 质量处理工单 | 执行人 | 填写分析并提交 |

## 7.12 常见问题

| 问题 | 处置 |
| --- | --- |
| 看不到“项目管理” | 产品经理无此菜单，项目执行由项目经理跟进 |
| 立项后想改预算 | 已提交不可改，撤回或走预算调整 |
| 特性版本号怎么来的 | 主开发版本加四位编号，审批通过时生成 |
| 迭代项目和原项目什么关系 | 新预立项 + 新项目，原项目数据不变 |
| 评审时委员没到齐 | 催办；委员须全部提交才能审结 |
| 产品发布后还能改内容吗 | 不能改已发布版本，走迭代 |
| 归档后发现漏了文件 | 归档不可逆，需在归档前核对交付文件 |
