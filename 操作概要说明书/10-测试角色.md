# 第 10 章 测试主管与测试总监（`TM` / `TGM`）

## 10.1 定位与角色构成

测试岗位在系统里有三种身份，容易混淆，先分清：

| 身份 | 角色码 | 来源 | 菜单数 | 职责 |
| --- | --- | --- | --- | --- |
| 测试主管 | `TM` | 立项或子项目上被指定为“测试主管” | 10 | 组件级测试下发、测试工单最终审核、缺陷反馈管理 |
| 测试总监 | `TGM` | 机构“测试部”负责人 | 10 | 同测试主管，另可看全部子项目的测试汇总 |
| 测试工程师 | 无独立角色（`STAFF`） | 不任命 | 8 | 执行测试工单、下发缺陷、提交测试交付 |

三点必须记住：

1. **测试主管不是团队管理里任命的**，而是在立项申请或子项目中把某人指定为“测试主管”，该人重新登录后自动获得 `TM`。
2. 测试主管的 `TM` 跟随项目：只对被指定为测试主管的项目与子项目生效，不是全机构通用。
3. 测试工程师不需要任何角色，靠项目经理下发测试工单即可工作。

| 项 | 说明 |
| --- | --- |
| 清单 | 在测项目列表、单元测试管理、缺陷反馈管理、测试执行汇总（`520801`）、绩效/盘点 |
| 页签 | 绩效/盘点中可见管理驾驶舱、项目仪表盘、组织工作量；不可见物料盘点 |
| 不包含 | 预立项、立项、项目管理、研发管理、系统工程、物料、仓库、库存、产品管理、质量管理 |
| 主要交接对象 | 项目经理（工单与评价）、测试工程师（执行）、提出人（缺陷反馈复核）、产品经理（质量单） |

## 10.2 测试管理页的构成

入口：`研发管理 > 测试管理`（资源号 `5208`，路由 `/customer/test`）。

| 页签 | 内容 | 角标 |
| --- | --- | --- |
| 在测项目列表 | 本人作为测试主管的子项目与项目 | 无 |
| 单元测试管理 | 已立项项目列表，按项目下发组件级测试 | 无 |
| 缺陷反馈管理 | 本子项目的缺陷反馈单 | `bugfeedbackNum` |
| 测试执行汇总 | 全部在测项目的测试执行统计（`520801`） | 无 |

“在测项目列表”有两张表：

| 表 | 列 | 操作 |
| --- | --- | --- |
| 子项目表 | 项目编号、子项目名称、项目名称、项目经理、预算、开发版本、立项时间 | 【测试管理】（角标 `submitJobNum`） |
| 项目表 | 项目编号、项目名称、产品经理、项目经理、开发版本、立项时间 | 【单元测试管理】（角标 `submitJobNum_testTask`）、【执行数据】 |

“测试管理”打开的是子项目测试任务页（页签名“测试项目 : 子项目名”），列出本子项目全部测试工单与缺陷反馈；“单元测试管理”打开的是预立项级组件测试页（页签名“单元测试管理 : 项目名”），用于对单个特性下发组件级测试。

## 10.3 测试任务审核（核心职责）

### 10.3.1 适用角色与目的

测试主管。目的：审核测试工程师提交的测试工单，确认测试覆盖与结论，通过后研发工单才回到项目经理评价。

### 10.3.2 入口

`测试管理 > 在测项目列表 > 子项目行【测试管理】 > 任务审核`；也可从 `执行管理 > 待办 > 测试工单` 进入。

### 10.3.3 前置条件

- 测试工单状态为 `SUBMIT`，下一节点为本人。
- 该子缺陷（如有）已关闭；存在未关闭子缺陷时，测试工程师无法提交测试结果。

### 10.3.4 操作步骤

1. 打开待审核列表。
2. 打开测试工单，核对：测试要点、测试记录、缺陷清单与关闭状态、工时申报、对被测工单的评分。
3. 选择【批准】或【驳回】。
4. 驳回必须填写原因，工单回 `HANDLING` 给测试工程师。
5. 批准后工单转 `COMPLETED`。

### 10.3.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 审核结论 | 是 | 批准 / 驳回 |
| 审核意见 | 驳回必填 | 文本，记入工单过程 |
| 核准工时 | 否 | 与申报工时不一致时填写 |

### 10.3.6 结果与留痕

测试工单 `COMPLETED`；被测试的研发工单下一节点交回项目经理，由项目经理做作业评价；特性状态不变（仍 `DEVELOPING`），直到集成完成才转 `DEV_COMPLETE`。

测试工程师给出的评分会被项目经理在研发工单评价时的评分覆盖，最终以项目经理评分为准。

### 10.3.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 待审核为空 | 测试工程师未提交，或已审完 | 核对执行人待办 |
| 提交测试结果被拒，提示子缺陷未关闭 | 缺陷工单仍在办 | 催缺陷处理人闭环 |
| 驳回后特性停住 | 测试工单回执行人 | 修复后重提，无需重启流程 |
| 想改测试结论 | 已批准收口 | 通过缺陷反馈或质量单重新走流程 |

## 10.4 下发组件级测试

### 10.4.1 适用角色与目的

测试主管。目的：对单个特性（通常是分解出的子特性）下发组件级测试，验证组件内部逻辑。

### 10.4.2 入口

`测试管理 > 单元测试管理 > 项目行【单元测试管理】 > 特性行【下发】`。

### 10.4.3 前置条件

- 项目已立项（`SETUPED` 及以后）。
- 目标特性处于 `DEVELOPING` 或更后状态。
- 测试执行人为本机构在职成员。

### 10.4.4 操作步骤

1. 在“单元测试管理”页签选择项目。
2. 展开特性列表，定位目标特性。
3. 点击【下发】。
4. 选择测试执行人。
5. 填写测试要点、计划工时与计划提交时间。
6. 提交。

### 10.4.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 测试执行人 | 是 | 在职成员，受负荷校验 |
| 测试要点 | 否 | 文本，写明验证项 |
| 计划工时 | 是 | 小时 |
| 计划提交时间 | 是 | 日期 |

### 10.4.6 结果与留痕

工单类型为“特性测试”，状态 `HANDLING`；执行人“执行管理”出现待办；特性过程记一条测试下发。执行人提交后回本人审核（见 10.3）。

### 10.4.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 特性列表为空 | 项目未立项或特性未启动研发 | 由项目经理先启动研发 |
| 下发按钮灰显 | 特性状态不支持 | 核对特性状态 |
| 提示超负荷 | 执行人未来 5 个工作日日均负荷超上限 | 换人或放宽时间 |

## 10.5 缺陷反馈管理

### 10.5.1 适用角色与目的

测试主管。目的：接收本子项目的缺陷反馈单，转成缺陷处理工单派给执行人，审核处理结果并提交结案反馈。

### 10.5.2 入口

`测试管理 > 缺陷反馈管理`。

### 10.5.3 前置条件

- 缺陷反馈单状态为 `SUBMIT`，且指向本人任测试主管的子项目。
- 缺陷反馈由任何成员（通常是客户服务代表、测试工程师）在“执行管理 > 缺陷反馈”提出。

### 10.5.4 操作步骤（转任务）

1. 打开缺陷反馈单，核对问题描述、影响范围、责成完成时间。
2. 点击【转任务】。
3. 选择处理人。
4. 填写任务说明与计划工时、时间。
5. 提交。

### 10.5.5 操作步骤（审核与结案）

1. 处理人提交分析（问题描述、本质分析、解决方案、输出指标、验证方法）后，单据回到本人。
2. 打开工单，核对分析与验证结果。
3. 批准或驳回；驳回回处理人补充。
4. 批准后填写结案反馈并提交。

### 10.5.6 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 转任务处理人 | 是 | 在职成员 |
| 任务说明 | 否 | 文本 |
| 计划工时 / 计划提交时间 | 是 | 数值与日期 |
| 结案反馈 | 是 | 文本，写清关闭依据 |

### 10.5.7 结果与留痕

| 动作 | 状态 |
| --- | --- |
| 转任务 | 工单类型“缺陷处理” `HANDLING`；缺陷反馈单据保持 `SUBMIT` |
| 处理人提交 | 缺陷反馈 `JOB_SUBMIT`；工单 `SUBMIT`，下一节点本人 |
| 本人批准 | 工单 `COMPLETED` |
| 本人提交结案反馈 | 缺陷反馈 `RECHECK`，回原提出人复核 |
| 提出人复核通过 | 缺陷反馈 `ARCHIVED` |
| 提出人复核不通过 | 缺陷反馈 `REJECT`，重新出现在本人列表 |

### 10.5.8 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 缺陷反馈不在列表 | 不属于本人任测试主管的子项目 | 由该子项目测试主管处理 |
| 提出人复核不通过 | 结案理由不充分 | 补充说明或重新转任务处理后再次提交结案 |
| 单据长期停在 `REJECT` | 未再次提交 | 打开单据重新提交结案反馈 |
| 缺陷与测试缺陷混淆 | 测试缺陷在测试工单内闭环，缺陷反馈是独立单据 | 两条流程不互通，分别处理 |

测试工单内的“缺陷”与“缺陷反馈”是两条独立流程：前者由测试工程师在测试工单中下发、由研发人员处理、由测试工程师关闭；后者是跨子项目的正式单据，走转任务—审核—结案—复核四段。

## 10.6 测试执行汇总

### 10.6.1 适用角色与目的

测试主管与测试总监（页签 `520801`）。目的：按项目汇总测试工单数量、完成率、缺陷数与通过率，用于周会与绩效核对。

### 10.6.2 入口

`测试管理 > 测试执行汇总`。

### 10.6.3 页面内容

| 区域 | 内容 |
| --- | --- |
| 汇总表 | 项目、子项目、测试工单总数、已完成数、缺陷数、已关闭缺陷数、通过率、平均工时 |
| 明细下钻 | 点击行展开该子项目的测试工单清单 |

### 10.6.4 操作要点

1. 数据为实时统计，不做快照，刷新即最新。
2. 通过率按“测试结论为通过”的工单占比计算，被驳回重做的工单只计一次。
3. 该页只为查看，不提供任何修改入口。

## 10.7 测试总监（`TGM`）的额外视角

测试总监与测试主管菜单相同（10 项），差别在数据范围：

| 维度 | `TM` | `TGM` |
| --- | --- | --- |
| 数据范围 | 本人任测试主管的项目与子项目 | 本机构全部在测项目 |
| 来源 | 立项或子项目中指定 | 机构“测试部”负责人 |
| 组件级测试下发 | 可 | 可 |
| 测试工单审核 | 只审本人项目 | 只审本人任测试主管的项目，其余只读 |
| 人员与费率 | 无团队管理 | 无团队管理 |

测试总监不能代替测试主管审核其项目的测试工单，需要时由机构管理员调整子项目的测试主管。

## 10.8 测试工程师侧（简要）

测试工程师为 `STAFF`，详细步骤见 15.5，此处只列与测试主管衔接的四个动作：

| 动作 | 入口 | 结果 |
| --- | --- | --- |
| 接测试工单 | `执行管理 > 测试工单 > 任务处理` | 无状态变化，进入处理 |
| 测试领料 | 测试工单内【物料申请】 | 领料单走项目经理审批与物料管理员发料 |
| 下发缺陷 | 测试工单 > 【缺陷处理】 > 新建缺陷 | 缺陷工单 `HANDLING`，工时 0，派给研发人员 |
| 提交测试交付 | 测试工单 > 【测试交付】 | 填工作描述、测试要点、对被测工单评分，提交后到测试主管 |

存在未关闭子缺陷时，测试工程师无法提交测试结果；测试主管在审核时也必须核对缺陷是否已关闭。

## 10.9 边界与交接

| 不做的事 | 由谁做 |
| --- | --- |
| 签发研发工单、下发集成工单 | 项目经理（9.8、9.9） |
| 研发工单的最终评价 | 项目经理（9.10） |
| 审批物料与费用 | 项目经理（9.11、9.12） |
| 质量单（客户质量反馈）处理 | 产品经理（7.8） |
| 指定测试主管 | 立项申请人或子项目创建人（7.5、9.3） |
| 调整测试人员的职级与费率 | 机构管理员（5.5、5.6） |

交接清单：

1. 立项批准后重新登录，确认侧栏出现“测试管理”与“绩效/盘点”。
2. 项目进入研发后，先确认被测特性已启动研发，再下发组件级测试。
3. 测试工单提交后及时审核，避免阻塞项目经理的研发工单评价。
4. 缺陷反馈复核不通过时，先补充分析再提交结案，不要反复空转。
5. 子项目评审前，配合项目经理核对测试与缺陷记录是否齐全。

## 10.10 常见问题

| 问题 | 答复 |
| --- | --- |
| 为什么我在团队管理里被任命了但还是看不到测试管理 | 测试主管不在团队管理任命，须在立项或子项目中指定测试主管后重新登录 |
| 为什么我只能看到部分子项目 | `TM` 跟随项目，只对被指定的项目生效 |
| 测试工单能否自己下发给自己 | 可以，但不建议，审核与执行应由不同人承担 |
| 测试评分与项目经理评分哪个算 | 项目经理评分覆盖测试评分，绩效以最终评分为准 |
| 组件级测试与子项目级测试有什么区别 | 组件级针对单个特性（特性测试工单），子项目级针对已交付研发成果（测试任务），入口与审核人相同 |
| 缺陷反馈能不能直接关闭 | 不能，须走审核批准与结案反馈，并由提出人复核 |
| 测试执行汇总的数据能不能导出 | 页面提供导出，导出内容与当前筛选一致 |
| 测试主管能不能改特性状态 | 不能，特性状态由研发与评审流程推进 |
