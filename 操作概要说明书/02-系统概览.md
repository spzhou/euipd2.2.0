# 第 2 章 系统概览

## 2.1 系统定位与总体架构

EUIPD 是按 IPD 体系组织研发过程的管理系统：以“需求 → 特性 → 预立项 → 立项 → 子项目 → 研发与工单 → 测试与质量 → 三级评审 → 归档 → 产品发布”为主线，把预算、物料、工时、档案、评审与统计挂在同一条数据链上。使用者不直接面对“模块”，而是面对菜单与单据状态。

系统由前端与四个后端进程组成，均通过网关访问：

| 进程 | 端口 | 上下文 | 职责 | 使用者的感知 |
| --- | --- | --- | --- | --- |
| gateway | 9000 | 无 | 路由、令牌验签、模块操作鉴权、请求头改写 | 浏览器唯一入口；无权限时返回拒绝 |
| system | 9001 | `/system` | 登录、令牌、用户、机构、角色、权限覆盖、验证码与短信 | 登录页、机构/团队、团队管理 |
| customer | 9005 | `/customer` | 研发业务主数据、工单、评审、预算费用、物料仓库、流程引擎、统计 | 侧栏“研发管理”组下绝大多数菜单 |
| file | 9003 | `/file` | 对象存储、上传下载、富文本、正式文件生成、在线编辑回调 | 档案管理、附件、Word 导入导出 |
| ftp | 9007 | `/ftp` | 单文件上传（上限 50 MB） | 大附件上传通道 |

数据与基础设施：MySQL 单库 `mycourse_bk`，业务表以 `customer_id` 做行级租户隔离，由租户拦截器自动追加条件；Redis 承载登录失败计数与锁定、令牌吊销、角标缓存；MinIO 承载文档与图片对象。

前端为 Vue2 单页应用，登录后进入 `/welcome` 工作台，侧栏与顶栏由壳层渲染。使用者在浏览器中的三个位置需要先建立概念：

1. **侧栏**：三组菜单（超级用户、我的邮件、研发管理），可见项由角色决定，见 2.2 与 2.4。
2. **页签**：同一菜单内的分栏（如绩效/盘点的四个页签），另受按钮白名单约束，见 2.6。
3. **顶栏**：个人信息、修改密码、退出登录；页脚显示前后端版本号，报障时提供该版本号。

## 2.3 角色体系

角色不是“岗位字段”，而是登录时按任命关系即时计算出来的结果。同一人可同时具备多个角色，菜单取并集。

| 角色码 | 中文名 | 类型 | 获得方式 | 菜单数 | 章节 |
| --- | --- | --- | --- | --- | --- |
| `SUPER` | 平台超级管理员 | 平台身份 | 平台机构（`fm4ek0Zy`）的管理员 | 平台 1 项 | 第 4 章 |
| `STAFF` | 员工 | 默认身份 | 每名在职成员自动具备 | 8 | 第 15 章 |
| `ADMIN` | 机构管理员 | 机构身份 | 登录手机号等于机构联系电话 | 12 | 第 5 章 |

1. **岗位字段只作显示**。成员资料里填“产品经理”不会得到 `PDM`，必须在产品经理名单中任命。
2. **角色改变后须重新登录**。菜单在登录时随令牌下发，改任命、改管理员、改最终管理人后，当事人退出重登才生效。

## 2.5 角色从哪来

登录时系统按以下顺序计算角色，结果随登录载荷下发：

1. 每人先记 `STAFF`。
2. 登录手机号等于机构联系电话，追加 `ADMIN`。
3. 在最终管理人记录中，追加 `UltiMng`。
4. 在委员会、产品经理、项目经理、系统工程师名单中，分别追加 `IPMT`、`PDM`、`PJM`、`SM`。
5. 是任一子项目的测试主管，追加 `TM`。
6. 是产品中心、系统工程部、质量部、法规部、测试部、物料部的负责人，分别追加 `PDGM`、`SYSGM`、`QCGM`、`FGGM`、`TGM`、`MATM`。

任命动作集中在两处：平台超管在“机构/团队”设置管理员与最终管理人；机构管理员或最终管理人在“团队管理”维护四份资质名单与部门负责人。最终管理人在读取时自动计入四份资质名单，因此在资质设置中显示为“最终管理人（默认）”且不可移出。

`TM` 是唯一的例外：它不靠团队管理任命，只能在立项或编辑子项目时指定测试主管。机构没有子项目时，任何人都拿不到 `TM`。

机构覆盖：最终管理人可为本机构其他角色调整菜单，差异写入机构覆盖表。覆盖不作用于 `ADMIN` 与 `UltiMng`，这两类身份始终按平台模板执行。

## 2.6 权限的三层闸门

| 层 | 判定对象 | 表现 | 越权结果 |
| --- | --- | --- | --- |
| 菜单 | 资源号是否在本人可用清单 | 侧栏是否渲染该项 | 不显示 |
| 页签与按钮 | 按钮资源号或“模块:操作” | 页签、按钮是否可点 | 不显示或置灰 |
| 接口 | 令牌中的模块操作范围 | 请求是否被受理 | 返回拒绝码，页面提示无权限 |

三处判定都通过才视为有权。实际操作中会遇到三种“做不到”：

1. **侧栏没有这个菜单**：角色未授予，或机构覆盖被调整。按 2.4 核对本角色是否应有该项。
2. **直接输入地址被弹回工作台**：菜单未授予时路由守卫不放行。
3. **页面能进但保存失败**：菜单已授予而模块操作不足，例如只读角色尝试提交。

遇到第 3 种时按附录 B 查该页面所属模块，再到第 18.1 节的三层闸门与附录 A 的角色页签矩阵确认是本角色本就不具备，还是任命或覆盖配置有误。

## 2.7 业务对象与状态族

使用者判断“单子在哪一步”靠状态码。状态码全表与中文对照见附录 D.4，拒绝码见第 18.4 节；这里先建立对象与状态族的对应：

| 对象 | 状态族（节选） | 详见 |
| --- | --- | --- |
| 需求 | `SAVED` → `SUBMIT` → `COMPLETED` / `ABANDON` | 15.3 |
| 特性 | `SAVED` → `SUBMIT` → `EXAMINE` → `APPROVED` → `SETUPED` → `DEVELOPING` → `DEV_COMPLETE` → `REVIEW` → `ARCHIVED` | 7.4 |
| 预立项 | `DRAFT` → `ACTIVE` → `CONVERTED` / `CLOSED` | 7.2 |
| 项目 | `SETUP_EDIT` → `SETUP` → `SETUPED` → `ONGOING` → `REVIEW_PRO` → `COMPLETE` → `ARCHIVED` | 9.2 |
| 子项目 | `SETUPED` → `ONGOING` → `REVIEW_SUBP` → `COMPLETE` | 9.3 |
| 工单 | `HANDLING` → `SUBMIT` → `COMPLETED`（驳回回到 `HANDLING`） | 15.4 |
| 评审 | 主单 `HANDLING` → `COMPLETED`；结论通过、有条件通过、增补、驳回 | 9.13 |
| 质量反馈 | `SAVE` → `SUBMIT` → `SAVE_ANALYSIS` → `JOB_SUBMIT` → `RECHECK` → `ARCHIVED` | 11.2 |
| 费用申请 | `APPLICATION` → `APPROVED` → `SUPPLEMENT` → `PRE_COMPLETE` → `COMPLETE` | 15.13 |
| 档案申请 | `APPLICATION` → `APPROVED` / `REJECT` → `COMPLETE` | 17.11 |
