# 第 8 章 系统工程师（`SM`）

## 8.1 定位与菜单

系统工程师是研发主线的“技术把关人”：特性在进入产品经理审批前必须先由他给出审核意见；子特性分解完成后必须由他复核；他还是项目 BOM 复核人与特性／集成级 CBB 的系统工程署名。

| 项 | 说明 |
| --- | --- |
| 角色码 | `SM`，来自系统工程师名单 |
| 菜单 | 9 项：8 项通用 + 系统工程（资源号 `5221`，路由 `/customer/function`） |
| 页签 | 不显示“系统工程列表”页签（`522101` 只属 `SYSGM`），进入系统工程页只看到“预立项列表” |
| 不包含 | 预立项管理、立项管理、项目管理、研发管理、测试管理、物料、仓库、库存、产品管理、质量管理 |
| 主要交接对象 | 产品经理（审批）、项目经理（分解与研发）、执行人（定义与修订）、评审组长（评审意见） |

三点易误判：

1. 系统工程师在“系统工程”页能做的只有审核、复核、查看与系统任务，**不能审批特性**，批准权在产品经理。
2. “系统工程”菜单与“系统工程页签”（`522101`）不是一件事，后者只有系统总监 `SYSGM` 能看到。
3. 系统工程师是**任命**产生的，不是岗位字段，改任后须退出重新登录。

## 8.2 系统工程页的构成

入口：`研发管理 > 系统工程`。

页面只有一个默认页签“预立项列表”，列出本机构全部预立项，按机构内创建时间排序。

| 列 | 说明 |
| --- | --- |
| 项目编号 | 预立项编号 |
| 项目名称 | 预立项名称，点击行可打开 |
| 产品经理 | `PDM` 名单中的预立项负责人 |
| 系统工程师 | 预立项上指定的 `SM` |
| 开发版本 | 主开发版本，如 `01.00.0001` |
| 创建时间 | 创建时间 |
| 操作 | 特性定义、特性管理、系统工程、任务管理、执行数据 |

行内五个按钮的含义：

| 按钮 | 用途 | 角标 |
| --- | --- | --- |
| 特性定义 | 向执行人下发特性定义工单，或直接建立特性草稿 | 无 |
| 特性管理 | 打开本预立项的特性清单，查看状态、下一节点、过程记录 | `submitJobNum` > 0 时显示红点 |
| 系统工程 | 以结构树方式查看本预立项全部特性与子特性的层级关系 | 无 |
| 任务管理 | 打开本预立项的系统工程任务（含审核、复核类工单） | `taskSubmitJobNum` > 0 时显示红点 |
| 执行数据 | 结构化查看特性 → 子特性 → 工单 → 交付件的全部执行数据 | 无 |

点击任一按钮都会在顶部打开一个新的动态页签，页签名形如“特性管理 : CUS-预立项一”“任务:CUS-预立项一”；页签可关闭，关闭不影响数据。

## 8.3 特性定义下发

### 8.3.1 适用角色与目的

系统工程师。目的：当需求已下发而执行人尚未在需求工单中编写特性时，由系统工程师指定执行人并下发特性定义工单。

### 8.3.2 入口

`系统工程 > 预立项行【特性定义】`。

### 8.3.3 前置条件

- 预立项状态为 `ACTIVE`（已有已提交的需求或特性）。
- 目标执行人为本机构在职成员。

### 8.3.4 操作步骤

1. 在预立项列表定位目标预立项，点击【特性定义】。
2. 选择要定义的需求（或多条需求合并定义）。
3. 选择执行人。
4. 填写计划提交时间与计划工时。
5. 填写任务说明。
6. 提交。

### 8.3.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 需求 | 是 | 本预立项下已提交的需求 |
| 执行人 | 是 | 本机构在职成员，受负荷校验 |
| 计划提交时间 | 是 | 日期 |
| 计划工时 | 是 | 小时 |
| 任务说明 | 否 | 文本，写入工单 |

### 8.3.6 结果与留痕

工单类型为“特性定义”，状态 `HANDLING`；执行人“执行管理”出现待办与角标；需求转 `HANDLING`。

### 8.3.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 需求不在候选列表 | 需求未提交或不属于本预立项 | 由产品经理确认需求归属 |
| 提示工作超负荷 | 执行人未来 5 个工作日日均负荷超上限 | 换人或放宽计划时间 |
| 执行人看不到待办 | 未重新登录或未刷新 | 刷新；核对执行人是否选错 |

## 8.4 特性管理

### 8.4.1 适用角色与目的

系统工程师。目的：查看本预立项下全部特性的当前状态、下一节点与过程记录，判断哪些在等自己处理。

### 8.4.2 入口

`系统工程 > 预立项行【特性管理】`。

### 8.4.3 页面内容

| 区域 | 内容 |
| --- | --- |
| 列表 | 特性编号、特性名称、状态、下一节点、编写人、更新时间 |
| 行内操作 | 查看详情、查看过程、查看版本（继承关系） |
| 筛选 | 按状态、按关键字 |

### 8.4.4 操作要点

1. “下一节点”显示为本人姓名的记录即为待处理项。
2. 点开详情可看到六节正文（特性描述、接口定义、功能清单、性能指标、约束条件、验收标准）与历史审核意见。
3. 版本页签按时间倒序列出该特性的全部版本号，如 `01.00.0001-0001`、`01.00.0001-0002`。

### 8.4.5 异常与处置

列表为空通常说明该预立项尚无特性，或本人不是该预立项的系统工程师；跨预立项查看需由机构管理员修改预立项的系统工程或调整名单。

## 8.5 给出审核意见（核心职责）

### 8.5.1 适用角色与目的

系统工程师。目的：对执行人提交的特性做技术审核，给出意见后把工单转给产品经理审批。审核意见是特性审批的必备前置。

### 8.5.2 入口

两条路径等价：

1. `系统工程 > 预立项行【任务管理】 > 待审核特性`。
2. `执行管理 > 待办列表 > 特性定义工单 > 任务处理`。

### 8.5.3 前置条件

- 特性状态为 `SUBMIT`。
- 特性定义工单的下一节点为本人的姓名。
- 特性的六节正文已填写（特性描述与接口定义两节必须有正文）。

### 8.5.4 操作步骤

1. 打开待审核列表，逐条进入特性详情。
2. 通读六节正文，核对接口边界、功能清单与性能指标是否可测。
3. 在“审核意见”框填写意见，写清结论与待改点。
4. 保存意见。
5. 对下一条特性重复 2 至 4。

### 8.5.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 审核意见 | 是 | 文本，记入特性过程与办理记录 |
| 是否退回 | 否 | 退回落回执行人；不退回则转产品经理 |

### 8.5.6 结果与留痕

意见写入特性过程；一条需求工单下的全部特性都给出意见后，工单下一节点自动转产品经理；特性状态仍为 `SUBMIT`，等待审批。

审核意见只是技术意见，**不改变特性状态**。特性被退回是产品经理的工单驳回动作（见 7.4），不是系统工程师的权限。

### 8.5.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 待审核列表为空 | 上一节点未提交，或已全部审完 | 核对特性状态与工单下一节点 |
| 给了意见但工单没转 | 同一工单下还有特性未给意见 | 逐条补全，系统按“全部给出才流转”判定 |
| 意见写错想改 | 意见已入过程记录 | 追加一条补充意见，不改历史记录 |
| 打开详情看不到正文 | 执行人只保存未填写正文 | 退回给执行人补写后再审 |

## 8.6 分解复核（核心职责）

### 8.6.1 适用角色与目的

系统工程师。目的：对项目经理审批通过的特性分解结果做整体复核，确认子特性拆分合理、无遗漏、无重复。复核不通过时整批回退。

### 8.6.2 入口

`执行管理 > 待办列表 > 复核单 > 任务处理`；也可从 `系统工程 > 预立项行【任务管理】` 进入。

### 8.6.3 前置条件

- 主特性状态为 `DECOMPOSED`。
- 项目经理已完成子特性逐条审批（子特性为 `SETUP`）。
- 分解工单状态为 `CHA_RECHECK`，已生成复核单且下一节点为本人。

### 8.6.4 操作步骤

1. 打开复核单。
2. 核对子特性清单：名称、描述、预算、责任人、覆盖范围。
3. 选择结论：
   - **复核通过**：填写意见，提交。
   - **不通过**：必须填写不通过理由，指明需补充的项，提交。
4. 确认。

### 8.6.5 字段说明

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 复核结论 | 是 | 复核通过 / 不通过 |
| 复核意见 | 不通过必填 | 文本；通过时建议写明认可理由 |

### 8.6.6 结果与留痕

| 结论 | 结果 |
| --- | --- |
| 复核通过 | 子特性转 `SETUPED`；主特性保持 `DECOMPOSED`；分解工单转 `EVALUATE`（回到项目经理评价）；子项目与项目预算按差额调整 |
| 不通过 | 复核单 `COMPLETED`；全部子特性回 `SAVED`；分解工单回 `HANDLING`，下一节点为原分解执行人；需重新分解审批后再生成新复核单 |

复核单本身无论结论如何都记为 `COMPLETED`，结论体现在子特性与分解工单的状态上。

### 8.6.7 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 复核单里子特性不全 | 项目经理只审批了部分 | 结论选不通过，退回补全后重新审批 |
| 复核通过后预算不对 | 子特性预算之和与项目预算不平 | 由项目经理在项目管理中按差额调整，复核人不再改动 |
| 复核不通过后执行人没收到 | 分解工单未回到 `HANDLING` | 核对分解工单状态与下一节点 |
| 想只退回其中一条 | 复核为整批判定 | 在意见中写明具体条目，整批退回后由执行人改单条 |

## 8.7 修订审批

### 8.7.1 适用角色与目的

系统工程师或产品经理（二者均可）。目的：对已批准特性的修订内容做技术审批，通过后系统合入主线并生成新版本号。

### 8.7.2 入口

`系统工程 > 预立项行【特性管理】 > 修订页签 > 审批`；或 `预立项管理 > 特性管理 > 修订审批`（产品经理侧）。

### 8.7.3 前置条件

- 特性原状态为 `APPROVED`。
- 修订工单的下一节点为本预立项的系统工程师（或产品经理）。
- 同一特性同时只允许一个修订在进行。

### 8.7.4 操作步骤

1. 打开修订工单，查看编辑记录（改动前后的对照）。
2. 核对改动是否与本特性范围一致、是否影响已锁定版本。
3. 选择【批准】或【驳回】，驳回必须填写意见。
4. 提交。

### 8.7.5 结果与留痕

| 结论 | 结果 |
| --- | --- |
| 批准 | 编辑记录合入主线；特性状态仍为 `APPROVED`；特性版本号末四位加一（如 `01.00.0001-0002`）；版本表新增一行，旧版本留档 |
| 驳回 | 编辑记录回 `SAVED`，退回原执行人；修订工单回 `HANDLING` |

已在预立项阶段完成修订的特性，进入立项时以最新版本号参与项目基线；立项后再修订须走迭代（见 7.10）。

### 8.7.6 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 想再发起一次修订被拒 | 已有修订在进行 | 等当前修订完成 |
| 批准后正文没变 | 打开的是旧版本页签 | 切到最新版本号查看 |
| 修订涉及主开发版本 | 版本已锁定 | 走迭代，不在修订中改版本 |

## 8.8 任务管理

### 8.8.1 适用角色与目的

系统工程师。目的：集中处理本预立项下与自己相关的工单，包括特性定义、审核、复核、系统任务与质量类工单。

### 8.8.2 入口

`系统工程 > 预立项行【任务管理】`，或 `执行管理` 待办列表。

### 8.8.3 页面内容

| 页签 | 内容 |
| --- | --- |
| 待办 | 下一节点为本人、尚未处理的工单 |
| 在办 | 已处理但流程未结束的工单 |
| 已办 | 已完成的工单，可查看交付件与办理记录 |

### 8.8.4 操作步骤

1. 进入待办页签，按工单类型排序（审核、复核优先处理）。
2. 打开任一工单，点【任务处理】。
3. 按工单类型完成对应动作（审核意见、复核结论、系统任务交付）。
4. 提交。

### 8.8.5 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 任务管理角标常亮 | 有待办未处理 | 进入待办清空 |
| 打开工单提示到审核页办理 | 该工单类型只在对应业务页处理 | 按提示转到审核页或复核单 |
| 已办里看不到交付件 | 工单尚未评价完成 | 评价完成后归档可见 |

## 8.9 执行数据与文档

### 8.9.1 适用角色与目的

系统工程师。目的：以结构树方式通览一个预立项从需求到工单交付件的全部执行数据，用于技术核查与评审取证。

### 8.9.2 入口

`系统工程 > 预立项行【执行数据】`（页签名“文档 : 预立项名”）。

### 8.9.3 页面内容

树形展开：需求 → 特性 → 子特性 → 工单（定义／研发／测试／集成／缺陷／质量）→ 交付件与附件。每个节点可查看状态、责任人、时间与文件。

### 8.9.4 操作要点

1. 该视图为只读，不在此处修改任何数据。
2. 特性评审前用它对委员取证，确认六节正文、物料清单、测试记录齐全。
3. 交付件可下载；下载权限受文档权限设置约束（见 11.4）。

## 8.10 物料管理与费用管理页签

系统工程页还提供两个与系统任务相关的页签：

| 页签名 | 入口 | 用途 |
| --- | --- | --- |
| 物料管理 : 预立项名 | 系统工程 > 预立项行相关操作 | 查看本预立项关联的物料清单与领退料记录（只读为主） |
| 费用管理 : 预立项名 | 同上 | 查看本预立项关联的费用申请 |

系统工程师不审批物料与费用，审批与发料分别由项目经理与物料管理员办理（见 9.12、13.6）。这两个页签的用途是核对技术选型与成本是否一致。

## 8.11 作为评审委员

### 8.11.1 适用角色与目的

系统工程师通常被指定为特性评审、子项目评审、项目评审的委员。目的：从技术完整性角度给出委员意见，供组长审结。

### 8.11.2 入口

`执行管理 > 待办列表 > 委员单 > 任务处理`。

### 8.11.3 前置条件

- 被发起人（项目经理）选为本次评审委员。
- 评审主单为 `HANDLING`。

### 8.11.4 操作步骤

1. 打开委员单。
2. 查看评审对象：特性清单、物料清单、测试与缺陷记录、交付件。
3. 填写评审意见（结论倾向 + 具体问题）。
4. 提交。

### 8.11.5 结果与留痕

委员单转 `SUBMIT`；组长在审结页可见全部委员意见。委员单提交后不可修改，如需补充须在组长审结前联系组长重新发起，或在意见中一次性写全。

### 8.11.6 异常与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 组长审结被拒，提示委员未全部提交 | 有委员未提交 | 由发起人催办；不得由组长代填 |
| 委员单不在待办 | 未被选为委员，或已提交 | 核对评审主单的委员名单 |
| 想改已提交的意见 | 委员单已锁定 | 通过评审通知或线下补充，不重开委员单 |

## 8.12 作为项目 BOM 复核人与 CBB 技术署名

三处与系统工程师相关的“署名式”职责，均不产生单独的审批入口：

| 场景 | 系统工程师的作用 | 触发方式 |
| --- | --- | --- |
| 项目 BOM | 立项时指定的系统工程即本项目 BOM 复核人 | 在立项申请中指定，随项目基线固化 |
| 特性级 CBB | 特性发布为 CBB 时，系统工程师字段取项目的系统工程师 | 评审结论选“作为特性发布”时自动写入 |
| 集成级 CBB | 子项目评审通过并发布时，CBB 定义工单的系统工程师字段取项目的系统工程师 | 子项目评审组长审结后自动写入 |

这三处不生成“系统工程师审核单”，因此系统工程师在待办中看不到对应事项；如发现署名错误，须由产品经理在 CBB 描述中更正或由机构管理员调整项目团队。

## 8.13 边界与交接

| 不做的事 | 由谁做 |
| --- | --- |
| 审批特性、核定功能预算 | 产品经理（7.4） |
| 审批子特性与核定分解预算 | 项目经理（9.6） |
| 下发研发、测试、集成工单 | 项目经理（9.8） |
| 审批领料、退料、物料处置 | 项目经理（9.12） |
| 审结评审、决定是否发布 CBB | 评审组长，缺省为产品经理（7.6） |
| 修改预立项的系统工程师 | 机构管理员改名单，或产品经理在预立项修订中调整 |

交接清单：

1. 给出审核意见后，剩余动作在产品经理；可口头提示产品经理“已审完”。
2. 复核不通过后，剩余动作在原分解执行人；意见须写清待补项。
3. 委员单提交后，剩余动作在组长；委员不再介入。
4. 发现特性范围与技术风险，应在审核意见或委员意见中一次写全，不留在流程外沟通。

## 8.14 常见问题

| 问题 | 答复 |
| --- | --- |
| 为什么我的系统工程页没有“系统工程列表” | 该页签只属系统总监 `SYSGM`（`522101`） |
| 能不能替产品经理审批特性 | 不能，批准权在 `PDM` |
| 审核意见能改吗 | 已保存的意见入过程记录，只能追加补充意见 |
| 复核不通过要重走审批吗 | 要，子特性回 `SAVED`，执行人补充后需项目经理再次审批，再生成新复核单 |
| 复核通过后主特性为什么还是 `DECOMPOSED` | 分解完成的主特性在全部子特性归档前保持该状态，属正常 |
| 委员单能不能弃权 | 不支持弃权，必须给出意见；委员未全部提交时组长不能审结 |
| 能否自己发起特性评审 | 不能，评审由项目经理在研发管理或子项目管理中发起 |
| 系统工程师能否看到物料库存 | 无仓库与库存菜单；物料信息只能从特性或任务的物料页签查看 |
